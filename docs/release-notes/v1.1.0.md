# ProjectTenshin v1.1.0 — Linux x86_64 support, verified on an MSI Claw A1M

This release adds **Linux x86_64** as a full target beside ARM64/Snapdragon, and
it is verified on real hardware: the game builds, boots and runs from Steam's
Game Mode menu on an **MSI Claw A1M** (Intel Core Ultra 5 135H, Intel Arc iGPU)
running CachyOS with Steam in Game Mode over gamescope.

## What is new

### x86_64 Linux is a first-class target

- The runtime's Linux host layer is now shared by both architectures. The
  platform code moved from `platform/arm64/` to `platform/linux/` and its
  namespace from `projecttenshin::arm64` to `projecttenshin::host`, because the
  CPU-cluster classifier and the Vulkan helpers were never ARM-only: the
  classifier reads `cpufreq/cpuinfo_max_freq`, which describes a Snapdragon's
  Prime/Gold/Silver tiers and an Intel hybrid part's P-cores/E-cores alike.
- **Hybrid-CPU thread pinning now works on x86_64.** `PROJECTTENSHIN_PIN_PERF=1`
  (the default) pins the guest's fiber thread to the fastest cluster — the
  P-cores of an Intel hybrid part — while the Vulkan driver and SDL3 worker
  threads stay unpinned across every online core.
- A new ROM-free package: `ProjectTenshin-Linux-x86_64-Vulkan.tar.gz`, built
  natively by `tools/build-linux-x86_64.sh`, holding the runtime self-test, the
  Linux host-layer test, the Vulkan hardware probe and the launcher script.
- `run_linux_vulkan.sh` is the Vulkan launcher for both targets: it prefers the
  Freedreno/Turnip ICD on aarch64, reports the available ICDs on x86_64, and sets
  the shader cache, resolution scale and pinning on either.
  `run_arm64_vulkan.sh` stays as the ARM64 entry point for v1.0.0's shortcuts and
  forwards to it.
- The presenter's shaderc fallback now also looks in `libs.x86_64/`, so a
  package can ship its own `libshaderc_shared.so.1` beside the runner.

### Steam Game Mode without a desktop file by hand

- New `tools/steam_shortcut.py` registers the game in Steam's library, which is
  what Steam's Game Mode menu reads. It edits `shortcuts.vdf` — a binary VDF
  file — with the key spelling Steam itself uses (`AppName`, `Exe`, `StartDir`,
  the rest lowercase), keeping every existing shortcut byte for byte, and
  refuses a file it cannot parse instead of overwriting it.
- `--restart-steam` stops Steam the only way that works in a Game Mode session:
  the session's supervising unit is stopped first, because `steam -shutdown` is
  answered by the session starting the client again within a second — and that
  new instance reads `shortcuts.vdf` before an entry written afterwards exists.
  The script then writes the file, starts the unit again, and `list` and `remove`
  manage what is registered.

### Tests that survive a real handheld

- `recomp-runtime-input-host-sdl` needs a machine with no gamepad attached, which
  an x86_64 handheld with Steam running never is: hhd's translation of the built-in
  pad and Steam's virtual controller already hold ports 0 and 1. It now skips
  (`SKIP_RETURN_CODE 77`) with that reason instead of failing.

### Building on a read-only distribution

- `build_game.sh` now looks for `cmake` and `ninja` in the build's own
  `private/venv` first, and installs them there when the system has neither.
  That is what let this release be built on CachyOS without ever needing a root
  password: both are Python packages, so no `sudo` is required.

### CI and packaging

- New workflow `.github/workflows/build-linux-x86_64.yml`: Python tooling tests,
  public-export verification, a full CMake build, the whole CTest suite, the
  x86_64 package, and — on a tag — its archive attached to the tag's release
  beside the ARM64 one.
- `tools/build-host-test.sh` and the new package script build for whichever
  architecture the host is.

## Verified on real hardware

Everything below was observed on the machine, not extrapolated: an **MSI Claw
A1M** (`MS-1T41`), Intel **Core Ultra 5 135H** (18 threads in three frequency
tiers the probe reports as `8 prime, 16 perf, 2 silver`), Intel Arc iGPU on Mesa
26.3.1 (`vulkan-intel`), SDL3 3.4.20, shaderc 2026.4, GCC 16.2.1, CachyOS (Arch
family), 16 GB RAM, Steam in Game Mode over gamescope.

### Build

- Built from a USA 3.0 disc (`default.xbe` sha256 `e523dd15…`) with the
  repository's own flow, `./build_game.sh`, and validated against the recorded
  program manifest `8e244632…` before it compiled.
- The lifter: **6937 functions, 6857 translated, 0 failed, 89 hand-written
  overrides, 0 unresolved stubs**, in 7 chunks.
- The runner is a native
  `ELF 64-bit LSB pie executable, x86-64`, linking the system `libSDL3.so.0`;
  `ldd` reports nothing missing.
- No root password was needed: CMake and Ninja came from `private/venv`.

### The game boots

- Headless run (`RECOMP_HEADLESS=1`): SDL3 audio up on PipeWire at 48 kHz
  stereo, presenter
  `initialized driver=vulkan scale=1.00 resolution=720x480 window=640x480
  widescreen=0 msaa=1x depth=d32s8 a8=1 water=modern freedreno=0`, then the
  guest ran to a clean `kind=normal-exit exit_code=0` after 1,419,503 kernel
  calls.
- The hybrid-CPU classifier did its job on x86_64: `heterogeneous CPU detected
  (18 online cores: 8 prime, 16 perf, 2 silver) -> guest pinned to perf cluster`.
- Audio over the run: `submitted_buffers=6398 dropped_buffers=0 underruns=1`.

### Steam Game Mode

- `tools/steam_shortcut.py add --restart-steam` wrote the library entry and
  restarted Steam; the file it writes is byte-identical to the output of
  ValvePython's `vdf.binary_dumps` for the same shortcut.
- Steam launched it: `GameAction [AppID 3440819849] : LaunchApp changed task to
  Completed`, and the chain it created ended in
  `recomp_launcher` (given the checkout as its argument) running on screen.
- Steam bound a controller config to that App ID (`Loaded Config for Last Resort
  Path for App ID 3440819849, Controller 0`), and SDL reports the Claw's pad as
  `Xbox 360 Controller`, which the runtime opens on port 0
  (`recomp input: gamepad 'Xbox 360 Controller' on port=0`).

### Test suites, on that machine

- Python tooling and custody tests: **94 run, OK** (2 skipped: the optional real
  extract-xiso check and a Windows-launcher-only keyboard test).
- CTest: **50 tests, 48 passed, 2 skipped** (`custom-music` needs an audio
  device the session did not provide; `input-host-sdl` needs a machine with no
  gamepad attached, and the Claw has two: hhd's translation of the built-in pad
  and Steam's virtual controller).

### Not verified in this release

- **Frame rate.** The verification runs were headless or the settings screen, so
  no FPS figure is claimed here. The ARM64 release's 60 FPS measurements were on
  a Snapdragon 8 Gen 3; an x86_64 figure needs a windowed session with the
  presenter's frame log, which this release does not include.
- **In-game controller input end to end.** The pad is opened by the guest and
  Steam binds a config for it, but no button press was injected to watch the
  game react.

## Upgrading

Existing ARM64 users are unaffected: `run_arm64_vulkan.sh` keeps working and
forwards to the shared launcher. Rebuild with `tools/build-arm64-game.sh` (or
`./build_game.sh` on the device) to pick up the runtime changes.

Nothing copyrighted is distributed: no disc, no generated game code, no assets.
Build from your own legally obtained disc.
